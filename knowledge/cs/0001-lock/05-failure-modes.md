# 락 장애 유형과 대응

## 쉬운 설명

락은 제대로 써도 제 역할을 못 하는 때가 있다. 두 사람이 서로의 열쇠를 기다리며 영원히 서 있거나(데드락), 서로 양보만 하다 아무도 못 들어가거나(라이브락), 한 사람만 계속 밀려나거나(기아), 열쇠를 쥔 사람이 쓰러져 아무도 못 들어간다. 여러 건물이 함께 쓰는 열쇠함에서는 쓰러진 줄 알고 새 열쇠를 줬는데 앞사람이 다시 일어나 **두 사람이 동시에 들어가는** 일까지 생긴다.

## 일반 설명

> 이 문서는 락이라는 장치가 제 기능을 못 하는 **방식**을 솔루션 공통으로 다룬다. 솔루션별 감지·복구 절차는 [Java 락 — 장애 대응](../../java/0002-java-lock/05-failure-modes.md), [MySQL 락 — 장애 유형](../../database/0004-mysql-lock/05-failure-modes.md), [Redis 락 — 장애 유형](../../database/0005-redis-lock/05-failure-modes.md)에 있다. 사람이 잘못 써서 생기는 문제는 [흔한 함정](./04-pitfalls.md).

### 1. 장애 유형 한눈에 보기

| 장애 유형 | 위반되는 성질 | 증상 | 일어나는 층 |
|---|---|---|---|
| **데드락** | 진행 | 일부 요청이 영원히 응답 없음 | 전 층 |
| **라이브락** | 진행 | CPU는 쓰는데 진척 없음 | 재시도·양보가 있는 곳 |
| **기아** | 한정 대기 | 특정 요청만 계속 실패·지연 | 비공정 락, 읽기/쓰기 락 |
| **우선순위 역전** | 한정 대기 | 높은 우선순위 작업이 낮은 작업 뒤에 멈춤 | OS·실시간 시스템, 우선순위 있는 스레드 |
| **락 convoy·경합 붕괴** | 처리량 | 부하가 늘수록 처리량이 오히려 감소 | 핫 락, 핫 로우, 핫 키 |
| **보유자 정지** | 진행 | 대기자 누적 → 풀 고갈 → 연쇄 장애 | 전 층 |
| **보유자 사망 (고아 락)** | 진행 | 아무도 획득 못 함 | 해제 보장이 없는 락 |
| **lease 만료 후 이중 보유** | **상호 배제** | 두 보유자가 동시에 쓰기 → 데이터 손상 | 분산 락 |
| **락 서비스 중단** | 가용성 | 아무도 락을 못 얻음 | 분산 락 |

각 유형은 장애 지점 → 원인 → 영향 → 대응 순으로 쓴다.

### 2. 데드락

- **장애 지점**: 서로를 기다리는 둘 이상의 보유자.
- **원인**: Coffman 등(1971)의 **네 조건이 모두** 성립할 때만 생긴다.

| 조건 | 뜻 | 하나를 깨는 방법 |
|---|---|---|
| 상호 배제 | 자원을 한 번에 하나만 가짐 | 공유 가능한 자원으로 (읽기 공유, 불변) |
| 점유 대기 | 하나를 쥔 채 다른 것을 기다림 | 필요한 락을 **한 번에** 모두 잡거나, 못 잡으면 다 놓기 (`tryLock`) |
| 비선점 | 남의 락을 빼앗을 수 없음 | 타임아웃·롤백으로 강제로 놓게 함 |
| **순환 대기** | A→B→A처럼 대기가 원을 이룸 | **락 순서 고정** — 실무에서 가장 흔한 해법 |

- **영향**: 데드락에 걸린 요청이 멈추고, 그 요청이 쥔 다른 락까지 막아 영향이 번진다.
- **대응**: 층마다 다르다.

| 층 | 감지 | 해소 |
|---|---|---|
| JVM | 스레드 덤프·`ThreadMXBean`이 찾아 줌 | **자동 해소 없음** — 증거 수집 후 재시작 → [Java 장애 대응](../../java/0002-java-lock/05-failure-modes.md#3-복구-jvm은-데드락을-풀어-주지-않는다) |
| DB (InnoDB) | 대기 그래프에서 사이클을 즉시 감지 | 작은 트랜잭션을 롤백(ERROR 1213) → 애플리케이션이 재시도 → [MySQL 락 — 기다림과 데드락](../../database/0004-mysql-lock/02-overview.md#7-기다림과-데드락-처리) |
| 분산 락 | 보통 감지 없음 | TTL·lease 만료가 결국 풂 (그동안 멈춤) |

### 3. 라이브락과 기아

**라이브락**
- **원인**: 충돌하면 둘 다 물러났다가 **같은 간격으로** 다시 시도해 또 충돌한다. 같은 주기의 `tryLock` 재시도, 낙관적 락 재시도가 흔한 예.
- **영향**: 데드락과 달리 CPU를 쓰고 로그도 남지만 일은 진행되지 않는다.
- **대응**: 재시도에 **지터**(무작위 지연)와 지수 백오프, 재시도 횟수 상한.

**기아**
- **원인**: 비공정 락에서 새로 온 요청이 계속 끼어들거나, 읽기 락이 끊이지 않아 쓰기 락이 영원히 밀린다.
- **영향**: 평균 지연은 괜찮은데 꼬리 지연(p99.9)이 폭발한다.
- **대응**: 공정 락(처리량 대가), 쓰기 우선 정책, 보유 시간 단축.

### 4. 우선순위 역전

- **장애 지점**: 낮은 우선순위 작업이 쥔 락.
- **원인**: 낮음(L)이 락을 쥔 상태에서 높음(H)이 그 락을 기다리고, 중간(M)이 CPU를 차지해 L이 실행되지 못한다 → H가 M보다 늦어진다.
- **영향**: 1997년 **Mars Pathfinder**는 이 문제로 감시 타이머가 시스템을 반복 재시작시켰다.
- **대응**: **우선순위 상속**(락을 쥔 동안 L의 우선순위를 H로 올림), 우선순위 상한 프로토콜. 웹 서버에서는 드물지만, 배치와 실시간 요청이 같은 락·같은 DB 행을 다투면 같은 모양이 나온다 — 낮은 우선순위 배치가 행 락을 쥐어 사용자 요청이 밀리는 경우.

### 5. 락 convoy와 경합 붕괴

- **장애 지점**: 요청 대부분이 거치는 락 하나(전역 락, 핫 로우, 핫 키).
- **원인**: 대기자가 많으면 해제 → 다음 대기자 깨우기 → 문맥 전환 비용이 임계 구역보다 커지고, 깨어난 쪽이 다시 줄을 서는 행렬(convoy)이 생긴다.
- **영향**: 처리량 상한이 1 / (임계 구역 + 전달 비용)으로 내려가고, 부하가 늘수록 처리량이 떨어진다. 대기자가 스레드·커넥션을 붙잡아 다른 기능까지 멈춘다.
- **대응**: 락 분할(스트라이핑·키 단위), 원자 연산으로 대체, 큐로 직렬화, 쓰기 모으기(batch), 집계 분산(카운터 샤딩).

### 6. 보유자 장애: 사망과 정지

보유자가 **죽은 경우**와 **멈춘 경우**는 결과가 다르고, 층마다 해제 방식도 다르다.

| 층 | 해제 보장 | 보유자 **사망** | 보유자 **정지** (GC, I/O, 네트워크) |
|---|---|---|---|
| JVM | 프로세스 수명 | 프로세스와 함께 해제 | 대기자 누적. 상호 배제는 유지 |
| DB | 세션·트랜잭션 | 커넥션 종료 감지 후 롤백·해제 (감지까지 지연) | 트랜잭션이 열린 채 대기자 누적 → [MySQL 장애 유형](../../database/0004-mysql-lock/05-failure-modes.md#1-락-관련-장애-유형) |
| DB 이름 락 | 세션 | 세션 종료 시 해제. 장애 조치 후 새 primary에는 락이 없음 | 위와 같음 |
| Redis | TTL | TTL 뒤 해제 (그동안 대기) | **TTL 만료 → 이중 보유** (7절) |
| ZooKeeper·etcd | 세션·lease | 세션 타임아웃 뒤 해제 | 세션 만료 → 이중 보유 가능. 단, 순번으로 fencing 가능 |

- 해제 보장이 없으면 **고아 락**(영구 보유)이 되고, 해제를 시간으로 보장하면 **이중 보유**가 생긴다. 둘 중 하나를 고르는 것이고, 둘 다 없앨 수는 없다.

### 7. 분산 락: lease 만료 후 이중 보유

- **장애 지점**: lease로 해제를 보장하는 락(Redis, ZooKeeper, etcd)과 그 보유자.
- **원인**: 분산 환경에서는 보유자가 "죽었는지 느린지"를 구분할 수 없다.

| 시나리오 | 결과 |
|---|---|
| 작업이 TTL보다 오래 걸림 | 만료 → 다른 보유자 획득 → 동시 실행 |
| 긴 GC 정지·프로세스 일시 정지 | 정지 중 만료 → 깨어난 옛 보유자가 여전히 보유자라고 믿고 쓰기 |
| 네트워크 분리 | 보유자는 락이 있다고 믿지만 서버 쪽에서는 만료 |
| 락 저장소 장애 조치 | 비동기 복제로 락 기록 유실 → 새 보유자 (Redis) |
| 시계 점프 | TTL이 예상보다 빨리 만료 |

- **영향**: 상호 배제가 위반되어(이중 보유) 결제 이중 처리, 재고 음수, 파일 덮어쓰기.
- **대응**: 락 쪽에서는 이 문제를 **없앨 수 없다**. 보호 대상 쪽에서 막는다.
  1. **fencing token** — 보호 대상이 오래된 번호의 쓰기를 거부 → [개요 — Fencing token](./02-overview.md#8-fencing-token)
  2. **DB 제약·조건부 쓰기** — 유니크 키, `UPDATE ... WHERE version = ?`
  3. **멱등키** — 같은 요청은 두 번 처리해도 결과가 같게

```sql
-- 멱등키: 락이 뚫려도 같은 이벤트는 한 번만 처리
INSERT INTO processed_event (event_id) VALUES (:id);   -- event_id UNIQUE
-- 중복 키 오류면 이미 처리된 것 → 건너뜀
```

Redis에서 각 시나리오가 어떻게 일어나는지는 [Redis 락 장애 유형](../../database/0005-redis-lock/05-failure-modes.md)에 있다.

### 8. 락 서비스 중단

- **장애 지점**: 분산 락 저장소(Redis, etcd, ZooKeeper) 또는 DB.
- **영향**: 락을 쓰는 모든 기능이 멈춘다. 락 저장소가 단일 장애점이 된다.
- **대응**: 락을 못 얻을 때의 정책을 **미리** 정한다.

| 정책 | 맞는 경우 | 대가 |
|---|---|---|
| 작업 중단 (안전 우선) | 정확성용 — 결제, 재고 | 가용성 손실 |
| 락 없이 진행 (가용성 우선) | 효율용 — 배치 중복, 캐시 재계산 | 중복 실행 |

### 9. 적용 한계와 반례

락이라는 방법 자체의 전제가 성립하지 않는 조건이다.

| 적용 한계 | 반례 |
|---|---|
| **락은 조합되지 않는다** | 스레드 안전한 메서드 `withdraw()`와 `deposit()`을 이어 부른 이체는 스레드 안전하지 않다. 더 큰 락이 필요하고, 그 락이 다시 데드락 위험을 만든다 |
| **락은 협조하는 코드만 막는다** | Redis 락으로 주문 처리를 막아도, 락을 모르는 관리자 배치가 같은 행을 고친다 |
| **분산 락은 장애 중 상호 배제를 보장하지 못한다** | GC 정지 중 lease 만료 (7절). 합의 기반 락도 세션 만료 뒤 옛 보유자를 막으려면 fencing이 필요하다 |
| **직렬 구간이 확장성의 상한** | 처리 시간의 10%가 같은 락 안이면, 서버를 무한히 늘려도 처리량은 최대 10배 (Amdahl) |
| **락 범위는 데이터 분포에 따라 달라진다** | 같은 범위 조건이 개발 DB에서는 좁게, 운영 DB에서는 넓게 잠긴다 → [MySQL 락 범위](../../database/0004-mysql-lock/02-overview.md#4-락-범위는-어떻게-정해지나-repeatable-read) |

### 10. 대응 절차 (공통)

| 단계 | 할 일 |
|---|---|
| 1. 감지 | 응답 지연, 대기 스레드·트랜잭션 급증, 데드락 감지 알람, 락 획득 실패율 |
| 2. 증거 수집 | 누가 쥐고 누가 기다리나 — JVM 스레드 덤프, `performance_schema.data_locks`·`sys.innodb_lock_waits`, 락 저장소의 키·TTL |
| 3. 격리·복구 | 보유자 종료(트랜잭션 `KILL`, 인스턴스 재시작), 고아 락 정리, 트래픽 차단 |
| 4. 분석 | 락 획득 순서, 락 안의 느린 작업, 보유 시간 분포 |
| 5. 재발 방지 | 순서 고정, 타임아웃, 단위 조정, 보호 대상 쪽 장치(제약·fencing·멱등키) |
