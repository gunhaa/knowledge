# 원장 사용 시 흔한 함정과 해결 방법

## 쉬운 설명

기입장을 잘못 쓰는 사람들은 대개 이렇게 한다. **틀린 줄을 지우개로 고치거나**, 줄 번호를 **시계를 보고 붙이거나**(그러면 두 사람이 동시에 써도 번호가 안 겹친다), **내 칸만 적고 돈이 어디서 왔는지는 메모로만** 남긴다. 당장은 잔액이 맞아 보이지만, 나중에 통장과 합계가 다를 때 원인을 찾을 수 없다.

## 일반 설명

> 원인이 **사용하는 쪽**(설계·코드·운영 절차)인 실수만 다룬다. 원장 시스템 자체가 제 기능을 못 하는 경우는 [장애 유형](./05-failure-modes.md). 용어는 [개요 2절](./02-overview.md#2-용어).

### 1. 요약

| 함정 | 분류 | 결과 | 해결 |
|---|---|---|---|
| 충돌을 못 잡는 번호 (`AUTO_INCREMENT`·시각) | 오해 | 동시 출금이 둘 다 성공 | 마지막 기입에서 계산한 순번 |
| 금액을 부동소수점으로 | 실수 | 합계 불일치 | 정수 최소 단위 또는 `DECIMAL` |
| 기입 `UPDATE`를 DB가 막지 않음 | 실수 | 이력이 근거가 못 된다 | 권한 + 트리거 |
| 잔액을 애플리케이션에서 계산해 덮어쓰기 | 안티패턴 | 갱신 유실 | 기입 덧붙이기 + DB 제약 |
| 시스템 계정 없이 시작 | 안티패턴 | 외부와 대사 불가, 나중에 옮기기 어려움 | 처음부터 복식부기 |
| 재시도마다 새 멱등키 | 실수 | 같은 거래가 두 번 | 요청을 만든 쪽이 키를 정하고 재사용 |
| 트랜잭션 안에서 외부 호출 | 안티패턴 | 락·커넥션 장시간 점유, 롤백해도 외부는 처리됨 | 대기 → 확정 |
| 대기 입금을 사용 가능 잔액에 포함 | 오해 | 취소된 입금을 이미 써 버림 | 사용 가능 = 확정 − 대기 중인 나가는 금액 |
| 모든 계정을 직렬화 | 실수 | 시스템 계정이 핫 계정 | 음수 금지 계정만 |
| 분산 락만 믿기 | 오해 | 락이 뚫리면 이중 처리 | DB 제약이 정확성을 맡게 |

### 2. 충돌을 못 잡는 번호

**오해**: "번호만 겹치지 않으면 순서가 보장된다."

```
A: 잔액 500 읽음 → AUTO_INCREMENT 101 발급 → 출금 400, 거래 후 잔액 100 기록
B: 잔액 500 읽음 → AUTO_INCREMENT 102 발급 → 출금 400, 거래 후 잔액 100 기록   ← 둘 다 성공, 실제로는 −300
```

- `AUTO_INCREMENT`, 채번 테이블, 시각(`created_at`)은 **요청마다 다른 값**을 준다. 같은 상태(잔액 500)를 보고 판단한 두 요청이 서로 다른 번호를 받으므로 충돌하지 않는다.
- 해결: 번호를 **읽은 상태에서 계산**한다(마지막 순번 + 1). 같은 상태를 본 요청은 같은 번호를 만들어 유니크 키에서 부딪힌다 → [트레이드오프 3.1](./03-tradeoffs.md#31-예-복식부기-원장에-순번-mysql).
- 시각은 조회·감사용이다. 같은 마이크로초에 두 행이 생길 수 있고, 서버마다 시계가 다르다.

### 3. 금액 표현

| 방식 | 문제 | 권장 |
|---|---|---|
| `FLOAT`/`DOUBLE` | 이진 부동소수점은 0.1을 정확히 표현하지 못해 `0.1 + 0.1 + 0.1 − 0.3`이 0이 아니다. 금액이 맞아도 **차변 합 = 대변 합 검사를 통과하지 못한다** | 쓰지 않는다 |
| `DECIMAL(19,2)` | 통화마다 소수 자릿수가 다르다 | 통화를 함께 저장하고 자릿수를 통화별로 |
| 정수 최소 단위 (원, 센트) | 표시할 때 자릿수를 알아야 한다 | 가장 안전. TigerBeetle은 128비트 정수만 쓴다 |

ISO 4217의 최소 단위 자릿수는 통화마다 다르다. 원·엔은 0, 달러는 2, 쿠웨이트 디나르는 3이다. "모든 통화는 소수 둘째 자리"라고 가정하면 일부 통화의 금액이 10배·100배 틀어진다. 포인트·재고 수량도 소수가 필요한지 처음에 정한다.

### 4. 기입을 고칠 수 있게 두기

- "덧붙이기만 한다"를 코드 규칙으로만 두면, 급한 장애 대응이나 데이터 보정 스크립트가 `UPDATE`를 실행한다. 그 순간부터 기입은 근거가 못 된다.
- 해결: 애플리케이션 계정에는 `SELECT`·`INSERT`만 주고, `BEFORE UPDATE`·`BEFORE DELETE` 트리거로 막는다 → [개요 3.1](./02-overview.md#31-확정된-기입은-고치지-않는다). 보정은 반대 거래로 한다 → [개요 3.2](./02-overview.md#32-정정은-반대-거래로).

**잔액 덮어쓰기**도 같은 뿌리다.

```sql
-- 안티패턴: 애플리케이션이 계산한 잔액으로 덮어쓰기
SELECT balance FROM account WHERE id = :wallet;        -- 500
UPDATE account SET balance = 100 WHERE id = :wallet;   -- 동시 요청도 500을 보고 100을 쓴다 → 출금 하나가 사라진다
```

갱신 유실이다. 락으로 막으면 락이 뚫렸을 때 그대로 재발한다. 기입을 덧붙이고, 잔액 규칙은 DB 안에서 검사한다(순번 + `CHECK`, 또는 `WHERE balance >= :amt` 조건부 `UPDATE`).

### 5. 시스템 계정 없이 시작

- 처음에는 고객 지갑만 있으면 될 것 같아 단식부기로 시작하고, 출처는 거래의 `source` 열로 남긴다.
- 그러다 PG 수수료, 부분 환불, 정산 지연이 생기면 "PG가 우리에게 줄 돈이 얼마인가"를 거래 속성을 집계해 계산해야 하고, 그 값이 맞는지 검증할 규칙이 없다.
- 복식부기로 옮기려면 과거 모든 거래에 시스템 계정 기입을 다시 만들어야 한다. 덧붙이기만 하는 원장이라 과거 기입을 고칠 수도 없으니, 이관 시점의 잔액으로 **기초 잔액 거래**를 넣고 그 뒤부터 복식부기로 쓰게 된다. 이관 전 기간은 대사할 수 없다.
- 해결: 외부와 주고받는 도메인이면 처음부터 시스템 계정 목록(자금, 청산, 수익·비용, 가계정)을 설계한다 → [개요 5절](./02-overview.md#5-시스템-계정).

### 6. 멱등키

| 실수 | 결과 | 해결 |
|---|---|---|
| 재시도할 때마다 키를 새로 만든다 | 키가 달라 중복으로 안 잡힌다 | 요청을 처음 만든 쪽(클라이언트·주문)이 키를 정하고, 재시도에 같은 키를 쓴다 |
| 키 충돌을 오류로 처리한다 | 사용자에게 실패를 보여 주고 또 재시도 | 충돌 = "이미 처리됨". 기존 거래 결과를 돌려준다 |
| 키만 같고 내용이 다른 요청을 허용한다 | 다른 금액의 요청이 "이미 처리됨"으로 묻힌다 | 키와 함께 요청 내용(금액·계정)을 비교해 다르면 거부 |

### 7. 외부 호출과 상태

- **트랜잭션 안에서 외부 결제·송금 API를 부르지 않는다.** 응답을 기다리는 동안 행 락과 커넥션을 쥐고, DB를 롤백해도 외부는 이미 처리됐을 수 있다.
- 해결: 대기로 먼저 커밋 → 외부 호출(거래 ID를 외부 멱등키로) → 결과에 따라 확정·취소. 전이는 `WHERE status = 'pending'` 조건부로 해서 둘이 동시에 확정하지 못하게 한다 → [개요 7절](./02-overview.md#7-상태-대기--확정).
- 대기 중인 **들어오는** 금액을 사용 가능 잔액에 넣지 않는다. 취소되면 이미 쓴 돈을 되돌릴 곳이 없다.

### 8. 분산 락만 믿기

- Redis 락으로 "계정 하나에 요청 하나"를 막고 DB에는 제약을 두지 않는 설계가 흔하다. 락이 TTL 만료·장애 조치로 뚫리면 이중 출금이 그대로 커밋된다 → [락 장애 유형](../../cs/0001-lock/05-failure-modes.md#8-락-서비스-중단과-고가용성-구성).
- 분산 락은 재시도를 줄이는 **효율용**으로 두고, 정확성은 순번 유니크·`CHECK`·멱등키가 맡게 한다.

### 9. 진단

| 증상 | 확인 |
|---|---|
| 차변 합 ≠ 대변 합인 거래가 있다 | 거래별 `SUM(CASE direction WHEN 'debit' THEN amount ELSE -amount END) <> 0` |
| 계정 잔액 캐시가 기입 합과 다르다 | 캐시 vs 기입 합 비교 쿼리를 주기적으로 |
| 같은 주문이 두 번 결제됐다 | 멱등키가 재시도에 유지되는지, 키 충돌을 오류로 처리하지 않는지 |
| 중복 키 오류가 급증한다 | 핫 계정. 계정별 쓰기량 확인 → [트레이드오프 3.3](./03-tradeoffs.md#33-핫-계정) |
| 기입 테이블에 `UPDATE`가 실행됐다 | 트리거·권한이 빠졌는지. binlog에서 `entry` 대상 UPDATE 이벤트 검색 |
