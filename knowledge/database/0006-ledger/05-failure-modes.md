# 원장 장애 유형과 대응

## 쉬운 설명

기입장이 제 역할을 못 하는 때는 **기입장 밖과 숫자가 안 맞을 때**다. 같은 영수증을 두 번 적거나, "곧 들어온다"던 돈이 끝내 안 와서 대기 줄이 계속 남거나, 통장 잔액과 기입장의 통장 칸이 다르거나, 기입장을 보관하던 곳이 불에 타서 마지막 몇 줄이 사라지는 경우다.

## 일반 설명

> 원인이 **원장 시스템과 그 주변**(저장소, 외부 연동, 배치)인 장애를 다룬다. 사용자가 설계·코드를 고쳐 해결하는 실수는 [흔한 함정](./04-pitfalls.md). 용어는 [개요 2절](./02-overview.md#2-용어). 각 유형은 장애 지점 → 원인 → 영향 → 대응 순이다.

### 1. 장애 유형 요약

| 장애 유형 | 장애 지점 | 영향 |
|---|---|---|
| 중복 기록 | 메시지·웹훅 재전달, 클라이언트 재시도 | 같은 거래가 두 번 반영 |
| 대기 거래 정체 | 외부 응답 없음, 확정 작업 중단 | 사용 가능 잔액이 묶임 |
| 외부 대사 불일치 | 자금·청산 계정과 외부 기록 | 원장 잔액을 믿을 수 없음 |
| 잔액 캐시 어긋남 | 계정 행의 잔액 캐시 | 음수 금지 검사가 틀린 값으로 |
| 핫 계정 처리량 붕괴 | 한 계정에 몰리는 쓰기 | 재시도 폭증 → 전체 지연 |
| 장애 조치 중 커밋 유실 | DB primary | 확정된 거래가 사라짐 |

### 2. 중복 기록

- **장애 지점**: 메시지 큐·웹훅·PG 콜백. 대부분 **최소 한 번**(at-least-once) 전달이라 같은 이벤트가 두 번 온다. 클라이언트도 타임아웃 뒤 재시도한다.
- **원인**: 처리 결과를 저장하기 전에 응답이 끊기면, 보낸 쪽은 실패로 보고 다시 보낸다.
- **영향**: 멱등 처리가 없으면 입금·적립이 두 번 반영된다.
- **대응**: 외부 이벤트 ID나 요청 키를 거래의 멱등키로 쓰고 유니크 제약을 건다. 키 충돌 = 이미 처리됨 → 기존 결과를 돌려준다. 이미 두 번 반영됐다면 고치지 않고 **반대 거래**로 상쇄한다.

### 3. 대기 거래 정체

- **장애 지점**: 대기 거래를 확정하는 경로. 외부가 응답하지 않거나, 결과를 받는 작업이 죽는다.
- **원인**: 외부 결과가 "성공·실패" 둘이 아니라 **"모름"**(타임아웃)으로 끝난다.
- **영향**: 홀드한 금액이 사용 가능 잔액에서 계속 빠져 있다. 고객은 돈이 있는데 결제가 거절된다.
- **대응**:
  - 대기 거래에 **만료 시각**을 두고, 만료되면 외부에 상태를 조회한 뒤 확정하거나 취소한다. TigerBeetle은 대기 전송에 timeout을 두어 시간이 지나면 자동으로 취소한다.
  - 상태를 모르는 채 취소하지 않는다. 외부는 성공했는데 원장만 취소하면 대사 불일치(4절)가 된다.
  - 대기 건수와 가장 오래된 대기 시간을 지표로 본다.

### 4. 외부 대사 불일치

- **장애 지점**: 자금 계정(회사 은행 계좌)과 은행 명세, 청산 계정(PG 미수금)과 PG 정산 파일.
- **원인**: 대기 거래 처리 오류, 외부의 수동 정정, 수수료·환율 차이, 정산 누락.
- **영향**: 원장 잔액이 실제와 다르다. 정산·보고가 틀린다.
- **대응**:
  - 매일 두 가지를 본다. **자금 계정 잔액 = 외부 명세 잔액**인가, **정산이 끝난 청산 계정이 0으로 돌아왔는가.** 둘 다 복식부기여서 쿼리 하나로 나온다 → [개요 5절](./02-overview.md#5-시스템-계정).
  - 건별로 맞추고, 맞지 않는 금액은 **가계정**으로 옮겨 원장 전체의 차변 합 = 대변 합은 유지한 채 조사한다.
  - 원인이 밝혀지면 가계정에서 올바른 계정으로 옮기는 거래를 추가한다. 원장을 외부에 맞춰 고치지 않는다.

### 5. 잔액 캐시 어긋남

- **장애 지점**: 계정 행에 잔액을 캐시하는 구성 → [트레이드오프 4절](./03-tradeoffs.md#4-잔액을-어떻게-얻나).
- **원인**: 기입과 캐시를 다른 트랜잭션에서 갱신하거나, 배치가 기입만 넣고 캐시를 놓친다.
- **영향**: 음수 금지 검사(`WHERE balance >= :amt`)가 틀린 값으로 통과·거부한다.
- **대응**: 기입이 원본이다. 주기적으로 캐시와 기입 합을 비교하고, 다르면 기입에서 다시 계산한다. 덧붙이기만 하는 구조라 언제든 다시 계산할 수 있다.

### 6. 핫 계정 처리량 붕괴

- **장애 지점**: 쓰기가 몰리는 고객 계정(인기 판매자, 이벤트 포인트 풀), 또는 실수로 직렬화한 시스템 계정.
- **원인**: 계정별 쓰기가 직렬화되어 있어 상한(커밋당 1ms면 초당 약 1,000건)을 넘으면 충돌·재시도가 늘고, 재시도가 다시 충돌을 만든다.
- **영향**: 그 계정이 끼는 모든 거래가 느려지거나 실패한다.
- **대응**: 시스템 계정은 직렬화하지 않는다. 고객 계정은 재시도에 상한·백오프·지터를 두고, 계정별 큐(효율용 분산 락 포함)나 묶음 처리로 줄인다 → [트레이드오프 3.3](./03-tradeoffs.md#33-핫-계정).

### 7. 장애 조치 중 커밋 유실

- **장애 지점**: 원장을 담은 DB의 primary.
- **원인**: 비동기 복제에서 primary가 커밋을 응답한 뒤 replica에 전달하기 전에 죽는다.
- **영향**: 고객에게 "완료"라고 응답한 거래가 새 primary에 없다. 외부(은행, PG)에는 처리됐는데 원장에는 없는 상태가 된다.
- **대응**: 반동기 복제, Group Replication, Raft 기반 저장소처럼 **커밋 응답 전에 다른 노드에 기록**되는 구성을 쓴다 → [락 장애 유형 — 고가용성 구성](../../cs/0001-lock/05-failure-modes.md#8-락-서비스-중단과-고가용성-구성), [MySQL 락 — 장애 조치](../0004-mysql-lock/05-failure-modes.md#3-장애-조치failover). 그래도 남는 차이는 멱등키 재시도와 외부 대사(4절)가 잡는다.

### 8. 탐지

| 검사 | 주기 | 이상이면 |
|---|---|---|
| 시산표: 전체 차변 합 = 대변 합 | 매일 | 차변 합 ≠ 대변 합인 거래 추적 |
| 자금 계정 잔액 = 외부 명세 | 매일 | 건별 대사, 가계정 (4절) |
| 정산 끝난 청산 계정 = 0 | 매일 | 미정산 건 추적 (4절) |
| 가계정 잔액 = 0 | 매일 | 조사 중인 건 처리 |
| 잔액 캐시 = 기입 합 | 매일·배치 후 | 캐시 재계산 (5절) |
| 대기 거래 수·최장 대기 시간 | 실시간 | 만료 처리 확인 (3절) |
| 계정별 충돌·재시도율 | 실시간 | 핫 계정 대응 (6절) |

### 9. 백업과 복구

- 덧붙이기만 하는 구조라 **특정 시점까지의 기입만 있으면 그 시점의 모든 잔액을 다시 만들 수 있다.** 시점 복구(PITR)와 잘 맞는다.
- 복구한 뒤에는 복구 시점 이후 외부에서 처리된 거래를 대사로 찾아 새 거래로 채운다.
